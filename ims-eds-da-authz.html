Authentication & Authorization across EDS and DA

How editing, publishing, and configuration permissions fit together
A separation-of-duties model for Edge Delivery Services + Document Authoring
Key takeaway

The short answer

For Editing

Use DA as the RBAC layer

Document Authoring decides who can edit what content — mapped by path and action across your content tree.

For Preview / Publish / Config / Runtime

Use EDS access config

Edge Delivery Services decides who can preview, publish, view protected content, and manage site configuration.

These are SEPARATE permission systems — design them that way from the start.
Identity

Adobe IMS: the identity foundation

Adobe Identity Management System (IMS) is the single source of truth for WHO a person is. Both DA and EDS authorization build on top of IMS identity and group membership.

1 · Users & identity

Users & identity

Every person authenticates through Adobe IMS (Adobe ID / Enterprise ID / Federated ID via SSO). Identity is managed centrally in the Adobe Admin Console.

2 · IMS groups

IMS Groups

Admins create groups in the Admin Console (user groups / product profiles) to represent business teams and roles — e.g. "Global Authors", "Brand A Authors", "Release Managers", "Platform Engineers".

3 · Membership by role

Users → Groups by role

People are added to the groups that match their job function. A user can belong to multiple groups. Group membership — not individual user grants — is what downstream systems consume.

4 · Federation / SSO

Federation / SSO

With Federated ID, group membership can be driven from the customer's own IdP (e.g. Azure AD / Okta) and synced into IMS, so joiner/mover/leaver is handled by existing enterprise identity processes.

Model people ONCE in IMS groups, then reuse those groups in both DA (editing) and EDS (runtime/config). Avoid per-user grants.

How it's managed & controlled
  • Groups created and owned in the Adobe Admin Console
  • Membership changes go through the Admin Console (or are federated from the customer IdP via SSO/SCIM)
  • Least privilege: broad read, targeted write/publish/config
  • Separation of duties: editing (DA) is distinct from publish/config (EDS)
How it's audited
  • Admin Console provides user/group membership visibility and audit logs of admin actions
  • DA editing rights are auditable via the DA permissions sheet (groups → paths)
  • EDS rights are explicit and reviewable in each site/org access.json (roles per principal)
  • Periodic access reviews: confirm each group still maps to the right paths/roles; remove stale membership
From IMS groups, authorization fans out two ways → DA grants editing rights by content path, and EDS grants preview / publish / config rights per org & site. The next slides show exactly how.
Architecture

The mental model

DA = who can edit content.  EDS = who can preview, publish, view protected content, or manage site/config.  Profiles = shared config inheritance, not primary editor RBAC.

admin config_admin config author basic_author publish basic_publish develop
config_admin is powerful at the SITE scope.
There is NO finer built-in role for "only edit one part of site config" — if someone can manage config for a site, they can manage it broadly.
Enterprise guidance: keep org admins very small; use site-level config admins sparingly; put most editorial governance in DA path-based rights.

▾ What do the Roles mean?
Roles map directly to the access.json for the org or site — e.g. admin.hlx.page/config/<org>/sites/<site>/access.json. Site-scoped roles extend or override org-level roles.
Structure

How org, profile & site fit together

LayerORG = Governance
A small number of platform owners, shared defaults, and shared conventions across the whole organization.
LayerPROFILE = Reusable config
Sidekick settings, shared code source / robots, common defaults. Sites inherit via extends.profile.
LayerSITE = Operational scoping
Preview / publish / config permissions, site-specific admins and publishers, and exceptions.
org = governance  •  profile = reusable config  •  site = operational scoping
